#### 1. CREATIVE CONCEPT & PROBLEM STATEMENT

- **Creative Twist / Re-imagining Angle:** You learn the OWASP Top 10 fastest by pulling them off. Each level is a tiny, self-contained toy application - a toy bank, a toy photo vault, a toy admin panel - presented as a heist: the briefing tells you the target ("read the vault owner's private note"), and the app is fully usable in front of you. One classic flaw is planted (a predictable ID in the URL, a client-side-only check, an injection-shaped search box), and everything you need is visible if you poke the way an attacker pokes. Cracking it triggers the vault-open moment, loot in the form of a clear write-up: the flaw's name, why it worked, and the small fix that closes it. The heist framing keeps the ethics clean: these are toys built to be robbed, and every level ends with the defense.
- **Core Problem & Target User:** Developers hear "never trust input" for years without ever seeing a trust assumption break; security concepts stick only when you've exploited one yourself. Target user: web developers who want security intuition, students, and puzzle gamers who like inspecting and poking systems.
- **Core Value Proposition:** Hands-on security intuition in a safe sandbox: feel each classic vulnerability from the attacker's side, then learn the fix that matters as a defender.

#### 2. USER STORIES

- **Primary User Story:** "As a developer, I want to exploit a real flaw in a toy app myself, so that the vulnerability class becomes something I recognize instinctively in code."
- **Secondary User Story:** "As a learner, I want each solved heist to end with the fix and the principle, so that attacking knowledge converts directly into defensive habit."

#### 4. DAY 1 POC EXECUTION SPECIFICATION

- **Minimal Technical Setup:** React, TypeScript, Vite, Tailwind CSS. Toy apps run entirely client-side with simulated backends (state in memory), so exploitation techniques operate on real in-page behavior with no server targets; heist content as typed scenario files.
- **Core 24-Hour Demo Flow:** The toy bank shows "Your accounts" with /account/1042 in the URL bar. Change the number, and you're reading someone else's balance - vault open. The loot card: "Insecure Direct Object Reference - the server trusted an ID without checking ownership. Fix: verify the session owns the record, server-side, every time." **Aha moment:** the attack taking three seconds and the fix being one line - the asymmetry is the whole lesson.

#### 5. ADOPTION OPPORTUNITIES & DRIVERS

- **Instant Onboarding Hook:** Level one is beatable by literally editing the URL - a thirty-second win that reframes security from theory to touch.
- **Growth Vector:** Each heist's loot card is a clean, quotable lesson developers share; engineering leads get a curriculum that beats a slide deck, and "I broke into a bank before breakfast" is a natural brag.

#### 6. RISKS & MITIGATION

- **Dual-use content:** Teaching exploitation needs care. Mitigation: all targets are self-contained client-side toys with no real infrastructure; techniques shown are the classic, publicly documented weakness classes taught in every security course; every level pairs the exploit with the defense, and framing is consistently "spot and fix this in your own code".
- **Toy versus real gap:** Players may overestimate their skill after simplified apps. Mitigation: write-ups state plainly what the toy omits (frameworks, WAFs, scale), and link the concept to how it appears in real stacks.
- **Hint design:** Too obscure and players bounce; too guided and nothing is learned. Mitigation: a three-rung hint ladder (nudge, method, walkthrough) with a score cost, and a debrief that works even after a full walkthrough.
- **Scope creep into a real lab:** Running real vulnerable servers invites abuse. Mitigation: the architecture stays client-side toys by design; anything infrastructure-shaped is out of scope permanently.
