SuperCollider, taken apart

An audio synthesis platform made of two programs that talk over a network protocol. Seven interactive steps: the client and the server, the node tree, SynthDefs, rates, buses, OSC and timing, and the language's patterns. Everything here models behaviour documented in the SuperCollider 3.14 help. The sounds are small browser previews, not SuperCollider itself.

Two programs, one protocol

"SuperCollider" names five things: an audio server, a language, an interpreter, the interpreter acting as the server's client, and the application bundling them. The two programs that matter are sclang (language, interpreter, client) and scsynth (the server, or its multicore sibling supernova).

What the client really sends

Pick a line of sclang. The server never sees it. It only receives the OSC messages the interpreter derives from it.

sclang line

The server "knows nothing about SC code, objects, Object Oriented Programming, or anything else to do with the SC language." It does no MIDI either: a client receives MIDI and converts it to OSC commands.

The node tree decides who runs first

  
Everything running on the server is a node: a synth or a group of nodes. The tree is the order of execution. Within each control cycle the server calculates nodes top to bottom, so a synth that reads another synth's output must sit after it.

Click the x on a node to send /n_free. Freeing a group frees everything inside it.

    

  

  
Group 0 is the root. When the server is booted from sclang, group 1 is the default group and the default target for new nodes. The sclang client begins handing out node IDs at 1000 (ServerOptions.initialNodeID). Sending /s_new with ID -1 makes the server pick the ID, so you cannot address that node later.

  
Order only matters when one synth reads another through a bus. Independent sources can sit anywhere. That is also why the next steps keep returning to buses.

  
Sources: https://doc.sccode.org/Guides/Order-of-execution.html, https://doc.sccode.org/Reference/Server-Architecture.html, https://doc.sccode.org/Reference/Server-Command-Reference.html (s_new add actions 0 to 4)







  
A SynthDef is a graph of unit generators

  
A SynthDef is the template the server builds synths from. sclang runs your function once, records which UGens were connected how, and ships that graph to the server by name. The UGen graph (what the server loads)

      

      

    

  

  
The definition file format starts with the four ASCII characters SCgf and a version, then lists constants, parameters (with names) and UGen specs. Each UGen spec has a class name, a calculation rate, input and output counts, and inputs that point at either a constant or another UGen's output. The table above is built that way. It is a faithful layout, not bytes captured from sclang, so small details (for instance how sclang optimises the multiplications) can differ.

  
UGens are plug-ins the server loads at start-up. Their names match the sclang classes used to build SynthDefs. doneAction: 2 (Done.freeSelf) tells the envelope to free the whole synth when it ends, so finished notes do not pile up in the tree.

  
Sources: https://doc.sccode.org/Classes/SynthDef.html, https://doc.sccode.org/Reference/Synth-Definition-File-Format.html, https://doc.sccode.org/Classes/EnvGen.html, https://doc.sccode.org/Classes/Done.html







  
Audio rate, control rate, once

  
The server computes sound in small chunks. A control period is one chunk of blockSize samples (default 64). Every UGen has a calculation rate: ar one value per sample, kr one value per block, ir once when the synth starts.

  

    

      
      
      
    

    
    

  

  

    
ar SinOsc.ar(220)
Calculated for every sample. Use it for anything you hear directly: oscillators, filters, reverb.

    
kr SinOsc.kr(220)
One value per block, so the curve steps. Cheap, and fine for slow movement: envelopes, LFOs, parameters. The staircase above is what a fast signal looks like at control rate.

  

  
Smaller blocks mean finer control and more per-block overhead. The default is 64 and it is a server option (-z on the command line, ServerOptions.blockSize). Changing it is rare.

  
Sources: https://doc.sccode.org/Classes/ServerOptions.html, https://doc.sccode.org/Reference/Server-Architecture.html, https://doc.sccode.org/Classes/UGen.html







  
Buses are the patch cables

  
Synths never connect to each other directly. They write to and read from numbered buses: one global array of audio buses and one of control buses. The lowest audio buses are the hardware outputs, followed by the inputs, and then private buses for internal routing.

  

    

      
Audio buses: three sources and a reverb

      

      
      
Writing to a bus with Out.ar adds to what is already there. ReplaceOut overwrites instead.

    

    

      
Bus levels (sum of amplitudes)

      

      

    

  

  
With the default options (2 output and 2 input channels), buses 0 and 1 reach the speakers, 2 and 3 are the inputs, and 4 is the first private bus. The reverb here reads bus 4, so it must run after every synth that writes to it (step 2).


  
Control buses

  
A control bus carries a slow signal. /n_map connects a synth parameter to a bus, so one LFO can move several synths. Toggle the mapping to see the parameter follow it.

OSC: the actual bytes, and timing

  
Open Sound Control messages are compact binary. An address, a type tag string, then arguments, everything padded to 4 bytes. The server also accepts bundles: messages wrapped with a time tag saying when to execute them.

  

    

      
      
      
      
    

    

    

  


  
Why timestamps matter

  
The client builds a note a little before it should sound, and the time it takes varies. Sent as plain messages, that variation is audible. Stamped with logical time plus a latency, the server plays each at the exact moment, as long as the message arrives before it is due.

  

    simulation of the documented principle
    

      
      
      
    

    
    

  

  
In sclang, latency is a server setting and Pbind imports it automatically. Notes triggered by live input (MIDI, GUI) should use no latency, because they want to sound as soon as possible. Sequencing wants latency. The value must cover generating the bundle and the server rendering the audio, and on a network it also absorbs the jitter.

  
Sources: https://doc.sccode.org/Guides/ServerTiming.html, https://doc.sccode.org/Reference/Server-Command-Reference.html, https://doc.sccode.org/Reference/Server-Architecture.html, https://opensoundcontrol.stanford.edu/files/OSC_in_SC_Server.pdf. Byte layout follows the OSC 1.0 specification.







  
From a pattern to a stream of notes

  
This is where the language earns its place. A Pbind binds keys such as \degree and \dur to value patterns and plays the resulting stream of Events. Each event becomes OSC for the server: usually a timestamped /s_new. Edit the pattern and read the messages it produces.

Events and the OSC they become

      

      
Degree to note uses the scale, then the root. With root 0, degree 0 lands on middle C (MIDI 60, the Event default). The server needs a frequency, so the Event computes freq = 440 * 2^((midinote - 69)/12). Times are beats on the pattern's TempoClock; the \tempo key sets its tempo (beats per second).

    

  


  
The chain

  

    
Pattern
Pseq, Prand, Pwhite: lazy descriptions of value streams.

    
Event stream
Pbind merges its streams into Events: key and value maps.

    
OSC bundles
Each Event plays a synth: s_new with the Event's values, stamped with the server latency.

  


  
Other things in the box

  

    
Non-real-time mode
scsynth can read a file of timestamped OSC commands and write an audio file instead of playing live. A score is just a list of messages like the ones above.

    
supernova
An alternative server that speaks the same OSC and can spread synths over several CPU cores. You choose scsynth or supernova as the server; sclang stays the client either way.

    
Plug-in UGens
Synthesis building blocks are binary libraries loaded at start-up. Add more and sclang classes with the same names let you use them.

    
Any client works
Anything that can send OSC can drive the server. The help describes definition files as writable by any program that knows the UGens.
