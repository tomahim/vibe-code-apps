The invariant editor owns procedure, tool use and completion, explicitly not subject matter. Its prompt reads like a troubleshooting manual: trace the workflow, fix the earliest observed divergence, and match each failure to the cheapest effective component. Tool error? Distinguish bad input from timeout or missing capability, give one bounded fallback and a stop condition. Mechanical repetition? A script. Recurring workflow? A skill with its trigger named. Ignored critical rule, repeatedly? Only then a defensive plugin.

"Invariant" means these fixes should hold across domains: checking that a written file is actually usable is as relevant to a legal memo as to a data pipeline. The editor is told to define what "enough evidence" means, reserve room for every required artifact, and reopen or mechanically check the deliverable, because a successful write call does not establish usability. In the paper's case study, the invariant edit was a guardrail forcing the agent to inventory all inputs and verify every output file.
